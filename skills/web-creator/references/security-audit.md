# セキュリティ監査（security-audit）

公開前と、機能を追加・変更したときに、Cloudflare が公開しているスキル security-audit でサイトのリポジトリ全体の脆弱性を調べ、見つかったものを直します。

- 出典: https://github.com/cloudflare/security-audit-skill（Cloudflare 製、MIT ライセンス）。Cloudflare の脆弱性探索の仕組みのもとになったスキルで、調査、候補の探索、別のエージェントによる反証、結果の検証、報告の6段階で進みます
- 使い方や必要なものが変わることがあるため、使う前にリポジトリの README を確認します

## 行うとき

| 場面 | 行うか |
|---|---|
| 公開前（quality-gate.md の健康診断のあと、公開の前） | 必ず行う |
| 機能の追加・変更（ページの種類を増やす、お問い合わせフォーム、SSR のページ、外部の埋め込み、GitHub Actions のワークフロー、依存パッケージの追加） | 必ず行う。公開する前に行う |
| デザインの刷新、ページ構成の変更 | 行う（スクリプトや外部の読み込みが変わるため） |
| 記事やお知らせの追加・修正、文言や画像の差し替えだけ | 行わない |
| 保守ルーティンでの依存パッケージの更新 | 行わない（runtime-update の `pnpm audit` で扱う）。更新に合わせてコードを書き換えた場合は、機能の変更として行う |
| 脆弱性のニュースを渡されたとき | SKILL.md の手順で関係を調べる。関係があって直した場合は、直した範囲を対象に行う |

自動修正のワークフロー（autofix）の中では行いません。

## 入れ方

サイトのリポジトリにはコミットせず、作業のたびに作業用の一時フォルダに clone し、その SKILL.md を直接読んで手順に従います。クラウドの作業環境は会話ごとに作り直され、会話の途中で `~/.claude/skills/` に入れたスキルが読み込まれるかは環境によって違うためです（Claude Code のプロジェクトのスレッドは、リポジトリの `.claude/skills/` も読まない。versions.md の「時点つきの事実」）。

作業用のフォルダは `/tmp/security-audit-skill-src` に固定します。Bash の呼び出しごとにシェルの変数は消えるので、変数に入れた一時フォルダの名前に頼りません。次のかたまりは、全体を1回の Bash の呼び出しで実行します。

```bash
set -eu
rm -rf /tmp/security-audit-skill-src
git clone --quiet --depth 1 https://github.com/cloudflare/security-audit-skill /tmp/security-audit-skill-src
git -C /tmp/security-audit-skill-src rev-parse HEAD   # 使った版。実行ログに書く
ls /tmp/security-audit-skill-src/skills/security-audit/SKILL.md
```

1. clone したら、使った版（コミット）を控え、実行ログに書く。前回の監査と同じ版かどうかを比べられるようにするため
2. `/tmp/security-audit-skill-src/skills/security-audit/SKILL.md` を読み、そこに書かれた手順で監査を進める。参照しているファイルも、同じフォルダの中のものを読む
3. 前回の監査と版が違うときは、SKILL.md を読んで、前回と使い方が変わっていないかを確かめてから使う

スキルの仕組みで読み込ませたい場合（会話の途中でもスキルとして呼べる環境）は、`npx -y skills@1.7.4 add https://github.com/cloudflare/security-audit-skill --skill security-audit --global --agent claude-code --yes` でも入れられます。`skills` の版は固定して使い、上げるときは公開から3日以上たった版にします。入れたスキルは、エージェントと同じ権限で動きます。

## 頼み方

security-audit は、明示的に「監査」と頼んだときだけ6段階すべてを行います（完全な監査）。次のように頼みます。

```
security audit this codebase（このリポジトリ全体のセキュリティ監査を、完全な監査として行う）。profile は <quick か standard>。
直し方の提案（remediation）は、security-audit.md の「直し方の決まり」に合うものにする:
指摘した箇所だけを直す最小の変更にし、厳しい CSP、CI の追加、ワークフローの全面的な書き換え、依存パッケージの一斉更新、Cloudflare のダッシュボードの設定変更は提案に含めない。
それらが要ると考えた場合は hardening（多重の守りの補足）として分けて書く。
```

- 進め方（profile）は、サイトの形で選びます。security-audit は小さい対象には `quick`（候補の探索を1回にし、検証の回数を減らす）を用意しています。証拠の基準（別のエージェントによる反証、要確認の扱い）は profile で変わりません

| サイトの形 | profile |
|---|---|
| 静的なページだけ（SSG）で、フォームや SSR のページがない | `quick` |
| お問い合わせフォーム、SSR のページ、外部の埋め込み、GitHub Actions のワークフローを足した・変えた | `standard` |
| 機能の変更の監査で、変えた範囲がはっきりしている | 変えたパスだけを対象にする（scoped run）。profile は上の表で選ぶ |

- 結果は既定の `~/security-audit-skill/<リポジトリ名>/run-<番号>/` に出させます。リポジトリの中には出しません
- 同じリポジトリで2回目以降に行うと、前回の結果を使って足りないところを重点的に調べます。同じ会話の中では前回の結果を残しておきます
- 並列のサブエージェントを多く使い、時間とトークンがかかります。静的なサイトなら短く済みます。始める前に、作業をコミットして push し、SITE.md の「制作の進み具合」を更新してから、オーナーに「公開前の安全確認をします。10分〜30分ほどかかり、Claude の利用量を多めに使います。Pro のプランでは、途中で利用の上限に当たることがあります（止まっても、上限が戻ってから続きから再開できます）。今始めてよいですか？」と聞きます（選択肢: 今始める / 上限が戻る時間に始める）
- 調べる対象のコード（ビルドやテスト）を動かす確認は、外部への通信を止めた隔離環境でしか行わない決まりになっています。作業環境がその条件を満たさない場合、確かめられなかった候補は「要確認」（needs_validation）として残ります。監査のためにネットワークの許可を広げることはしません

security-rules.md の決まりは、監査の中でも優先します。サブエージェントにも、機密情報が入るファイル（`.env*`、`.dev.vars`、鍵のファイル）を開かないこと、環境変数をまとめて表示しないことを伝えます。

## 結果の扱い

結果は confirmed（確定）、needs_validation（要確認）、rejected（否定された候補）の3つに分かれます。

1. confirmed は、すべて直す。直し方は下の「直し方の決まり」に合うものにする。実装は site-builder に渡し、`pnpm run build` を通してから、もう一度監査を頼んで直ったことを確かめる
2. needs_validation は、書かれている「確かめられなかった事実」を確かめられる範囲で確かめる。確定したら 1 と同じく直す。確かめられなければ logs/IMPROVEMENTS.md に足す
3. rejected と、ほかの守りで防げている「多重の守りの不足」（hardening）は、直さなくてかまわない。直すのは、下の「任意で入れてよいもの」に当たるものだけにする

重大度（severity）が high 以上の confirmed が残っている間は公開しません。直せない場合は、何が起きうるかと、直すために必要なこと（有料プラン、外部サービスの設定など）をオーナーに一文ずつ伝え、判断を待ちます。

オーナーには「安全確認で2件見つかり、どちらも直しました」のように、件数と対応だけを伝えます。見送った提案は、件数と理由をログにだけ残します（下の「記録」）。オーナーに判断を求めるのは、機能を外すか変えるときだけです。

## 直し方の決まり（公開と作業を止めない）

オーナーは開発に詳しくない前提です。安全のための変更でサイトの表示が崩れたり、公開や記事の更新が失敗し続けたりすると、オーナーは自分で戻せず、弱点そのものより困ります。security-audit も、ほかの守りで防げている守りの不足は脆弱性ではなく hardening として分け、直し方は「指摘した箇所を守る、いちばん狭い変更」を勧めています（SKILL.md の「Recommend the smallest effective source fix」と、README の「Design principles」）。このスキルでは、その考え方に次の決まりを足します。

### 採用する直し方

次のすべてを満たす直し方だけを採用します。

- 指摘された箇所だけを直す（入力の扱い、出力のエスケープ、リンクの属性、設定の1行など）
- `pnpm run build` が通り、直した箇所のページのプレビューで、表示、フォームの送信、計測（Cloudflare Web Analytics）が変わらない
- 直したページの Lighthouse の点数が下がらない（quality-gate.md の基準のまま）
- 公開の流れ（deploy.yml、autofix.yml、`.github/scripts/smoke.sh`）と CI の確認の数を増やさない
- 配布元のテンプレートから作ったファイル（templates/ の写し）を、サイトのリポジトリだけで大きく書き換えない

### 採用しない提案

次のような提案は、確定した脆弱性を直すためのものでも、そのままは採用しません。代わりの直し方を探し、見送ったことをログに残します。

| 提案の例 | 採用しない理由 | 代わりにすること |
|---|---|---|
| 厳しい CSP（`Content-Security-Policy` で nonce や hash を必須にする、`'unsafe-inline'` を一律に禁止する、`script-src` を自分のドメインだけにする）を `public/_headers` に入れる | Astro がページに書き込む小さなスクリプトやスタイル、Cloudflare が配信のときに差し込む計測のスクリプト、地図や動画の埋め込み、Turnstile が止まり、表示や送信が壊れる。記事の追加でページが変わるたびに崩れる原因になり、autofix は `public/_headers` を直せない | 入れない。危険な入力の扱いそのものを直す。外部の埋め込みは、画像とリンクに替えられないかを考える |
| CI に脆弱性の検査（CodeQL、Semgrep、Trivy などの静的解析、`pnpm audit` を必須の確認にする）を足す | CI が重くなり、誤検知や新しく見つかった弱点で、記事の更新の公開まで止まる。CI はビルドと公開後の確認だけにする方針（README の「CI は最小限」） | 足さない。監査は公開前と機能の変更時にエージェントが行い、依存パッケージの弱点は保守ルーティン（runtime-update の `pnpm audit`）で扱う |
| GitHub Actions のワークフローの全面的な書き換え（アクションをコミットの SHA で固定する、権限をジョブごとに細かく分ける、ジョブを分割する） | 配布元のテンプレートと形が変わり、スキルを更新して取り込むときに食い違う。公開や自動修正が止まっても、オーナーは原因を追えない | サイトのリポジトリでは直さない。テンプレートに由来する指摘は、logs/IMPROVEMENTS.md に種類「スキル」で足し、配布元で直す。外から入る値がコマンドに渡るなど、確定した high 以上の弱点だけは、その行だけを直す |
| 依存パッケージの一斉更新、メジャーバージョンの更新 | 公開から3日待つ決まり（`minimumReleaseAge`）と、メジャー更新を自動で入れない決まりを崩し、ビルドが壊れやすい | runtime-update の手順で、弱点を直す版だけを上げる |
| Cloudflare のダッシュボードの設定の変更（WAF のルール、Bot Fight Mode、Under Attack モード、HSTS の preload や `includeSubDomains`） | 公開後の確認や Lighthouse の計測が止められる。HSTS の preload は取り消しに時間がかかり、同じドメインのほかのサービスにも効く（取り消しにくい操作） | 行わない。弱点を防ぐのに要る場合だけ、何が起きうるかと、変えたときの影響をオーナーに一文ずつ伝えて判断を待つ |
| 機能を外す、動きを変える（フォームをやめる、埋め込みを消す、ページを非公開にする） | オーナーの目的が変わる | オーナーに選択肢を示して判断を待つ。high 以上の confirmed なら、判断が出るまで公開しない |

確定した脆弱性に、採用できる直し方が見つからない場合は、上の「結果の扱い」と同じく、何が起きうるかと、直すために必要なことをオーナーに一文ずつ伝えて判断を待ちます。medium 以下なら、ログと logs/IMPROVEMENTS.md に残して公開してかまいません。

### 任意で入れてよいもの

hardening のうち、次のように表示や公開に影響しないものは、手間が小さければ入れてかまいません。入れたら、直したページのプレビューで表示が変わらないことを確かめます。

- 外部へのリンクの `rel="noopener noreferrer"`
- `public/_headers` の `X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`
- フォームの入力の長さの上限（すでにある検証に足すだけのもの）

迷ったら入れません。入れなかった hardening は、件数だけをログに書きます。

## 記録

- 報告書（REPORT.md、findings.json など）は、サイトのリポジトリにコミットしません。直していない弱点の詳しい中身を残さないためです
- 実行ログ（logs/）に、行った日と使った版（コミット）、profile、件数（confirmed / needs_validation / rejected）、直した内容の要約、見送った提案の件数と理由（「直し方の決まり」の表のどれに当たるか）を書く
- SITE.md の「品質の記録」に、最後に監査した日と、その時点で残っている要確認の件数を書く
- 報告書の文章をログに写すときは、scripts/check_text.py で機密情報が含まれていないかを確かめる
