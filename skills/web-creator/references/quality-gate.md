# 公開前の健康診断（品質チェック）

公開前と大きな変更の後に、次の項目を確認します。結果はログに残し、オーナーには「4項目とも満点近くです」のように要約して伝えます。

## 1. Lighthouse

計測は、エージェントのクラウドの作業環境（VM）で `scripts/run_lighthouse.sh` を使って行います。作業環境のブラウザ（Chromium）と Lighthouse で、モバイル設定で測ります。オーナーに計測を頼んだり、外部の計測サービスを使ったりはしません。

### 測るページ

全ページは測りません。見た目と仕組みが同じページは点数もほぼ同じなので、ページの種類ごとに代表を1つずつ、多くても5ページまでにします。

| ページの種類 | 測るページ |
|---|---|
| トップ | トップページ（必ず測る） |
| お知らせ・ブログ | 一覧ページ1つと、画像のある記事ページ1つ（いちばん新しいもの） |
| 問い合わせ | 問い合わせページ（埋め込みのフォームがある場合は特に） |
| そのほか | 地図や動画などの埋め込みがあるページ、ほかと作りが違うページ |

1ページのサイトはトップページだけです。測ったページは SITE.md の「品質の記録」に書き、次からも同じページを測って点数を比べます。ページの種類を増やしたとき（例: 採用ページを足した）は、そのページを測るページに加えます。

### 測るとき

1. 公開前: ビルドして作業環境の中で配信し、主要ページを測る

```bash
bash <スキルの場所>/scripts/run_lighthouse.sh http://localhost:4321/ http://localhost:4321/news/sample/
```

2. 公開後: 本番のURLで、同じ主要ページをもう一度測る（Cloudflare 経由の配信で数値が変わるため）

```bash
bash <スキルの場所>/scripts/run_lighthouse.sh https://<サイトの名前>.<アカウントのサブドメイン>.workers.dev/
```

3. デザインやページ構成を変えたとき、外部の埋め込みを足したとき。記事の追加だけのときは測らない

| 項目 | 目標 | 届かないときに最初に疑うこと |
|---|---|---|
| パフォーマンス | 95以上 | 画像のサイズと形式、Webフォント、外部の埋め込み（地図、SNS、動画） |
| ユーザー補助 | 100 | コントラスト、alt、見出しの順番、ボタンやリンクの名前 |
| おすすめの方法 | 100 | コンソールのエラー、古い書き方、HTTPのままの外部リソース |
| SEO | 100 | title と description、リンクの文言、robots の設定、canonical |

Core Web Vitals の目安は、LCP 2.5秒以内、CLS 0.1以下です。INP は実際の利用者のデータでしか測れないため、計測ではトータルブロッキングタイム（TBT）を代わりに見ます。

外部の埋め込みが原因で目標に届かない場合は、削らずに「代わりの方法と、その場合の点数」をオーナーに示して選んでもらいます。

### 作業環境から本番のサイトに届かないとき

作業環境は、外への通信が許可された行き先に限られています。最初の設定では、公開したサイト（workers.dev や独自ドメイン）や、Lighthouse 本体の取得先に届かないことがあります。`run_lighthouse.sh` が「届きません」と止まったら、オーナーに許可を足してもらいます。設定を変えると、動いている会話にも1分くらいで反映されます。

**よくある問題**: ネットワークの許可の設定の画面は、Claude のデスクトップアプリのチャット（Cowork）と、コード（Claude Code）とで違います。片方の画面で案内すると、オーナーの画面に出てこないことがあります。そのため、案内の前にどちらで作業しているかを確かめ、案内を分けます。

1. SITE.md の「作業の環境」の「Claude で作業している画面」を読む。書かれていなければ、オーナーに選択肢をつけて聞き、答えを SITE.md に書く
   - 質問の例: 「いま Claude をどちらの画面で使っていますか？ A. チャット（左のメニューの『チャット』や Cowork） B. コード（左のメニューの『Code』、claude.ai/code）」
   - 「分からない」と言われたら、画面のスクリーンショットを貼ってもらって判断する
2. 答えに合わせて、次のどちらかを案内する

**チャット（Cowork）の場合**（3分くらい）

1. Claude の左下の自分の名前を押し、「設定」を開く
2. 「機能」を開く
3. 「外部ネットワークへの通信を許可」の欄で、許可する範囲を「パッケージマネージャーのみ」（Package managers only）にしたまま、追加で許可するドメインの欄にサイトのホストを1行ずつ入れて保存する

**コード（Claude Code）の場合**（3分くらい）

1. 会話の画面のいちばん上で、会話の名前の右にある「∨」を押す
2. 「Edit cloud environment」を押す
3. 「Network access」を「Custom」に変える
4. 「Allowed domains」にサイトのホストを1行ずつ入れ、「Also include default list of common package managers」にチェックを入れる
5. 保存する

新しい会話を始める画面からも、メッセージ欄の下の環境の選択から同じ設定を開けます。手順と表示名は、案内の前に Claude Code のドキュメント（https://code.claude.com/docs/en/cloud-environments の Network access）で確認します。

足すホストは、サイトのホスト（`*.<アカウントのサブドメイン>.workers.dev`、独自ドメインなら `example.co.jp` と `www.example.co.jp`）です。パッケージの配布元（npm）も使うので、既定の許可（パッケージマネージャー）は残します。

- 追加のドメインが効かないという不具合の報告があります（2026年10月時点）。足しても届かない場合だけ、計測のあいだ「すべてのドメイン」にし、終わったら元に戻すよう伝えます。守りが弱くなることも一文で伝えます
- Team・Enterprise のプランでは、この設定は組織の管理者しか変えられないことがあります。その場合は、管理者に同じ設定を頼んでもらいます
- 画面の表示名は変わることがあります。オーナーが見つけられないときは、スクリーンショットを貼ってもらって場所を伝えます
- 公開の前（account-setup.md の Cloudflare の手順）に済ませておくと、計測で止まりません

## 2. SEO（検索エンジン向け）

- すべてのページに固有の `<title>` と `<meta name="description">` がある
- `<link rel="canonical">` が本番URLを指している
- OGP（`og:title`、`og:description`、`og:image`、`og:url`）と `twitter:card` がある。OG画像は 1200×630
- `sitemap.xml`（`@astrojs/sitemap` で自動生成。1ページの LP でも入れる）
- `robots.txt` に `Sitemap: https://ドメイン/sitemap-index.xml` を書く
- 見出しは h1 が1つ、h2・h3 が順番どおり
- 引っ越しの場合は、旧URLから新URLへの 301 リダイレクトを `_redirects` に書く（migration.md）
- 公開後、オーナーの了承を得て Google Search Console にサイトを登録し、サイトマップを送信する。所有権の確認には Cloudflare の DNS に TXT レコードを追加する

## 3. AIO（AI検索・AIエージェント向け）

- `llms.txt` をサイト直下に置く。サイトの説明、主要ページへのリンク、問い合わせ先を Markdown で書く（templates/llms.txt）
  - Google は llms.txt を検索順位に使わないと表明しています（2026年5月の AI 最適化ガイドでも「作る必要はない」と記載）。一方で Chrome の Lighthouse には、AIエージェント向けの実験的な監査として llms.txt のチェックが加わりました。置いても不利益はないため置きますが、内容が古くなると AI に誤った情報を渡すので、ページを増やしたら更新します
- 各ページの冒頭で「何の会社か」「誰向けか」「どこにあるか」に一文で答える
- 会社名、住所、電話番号は全ページで同じ表記にする
- Cloudflare には AI のクローラーを遮断する設定があります。AI 検索に載せたいか、学習には使われたくないかをオーナーに聞き、ダッシュボードの設定と robots.txt を合わせます

## 4. 構造化データ（JSON-LD）とリッチリザルト

ページに表示している内容だけを書きます。表示していない情報や、事実と違う情報をマークアップすると、Google の手動による対策（ペナルティ）の対象になります。

| ページ | 使う型 | 注意 |
|---|---|---|
| トップ | `Organization`（店舗なら `LocalBusiness` の適切な下位型）、`WebSite` | 自社が自社につけたレビューや評価（`aggregateRating`）は書かない。リッチリザルトの対象外で、ガイドライン違反になり得る |
| 下層ページ | `BreadcrumbList` | パンくずを実際に表示している場合だけ |
| お知らせ・ブログ | `NewsArticle` または `BlogPosting` | `headline`、`datePublished`、`dateModified`、`author`、`image` |
| 求人 | `JobPosting` | 実際に募集中の求人だけ。締め切ったら外す |
| イベント | `Event` | 日時、場所、主催者 |

使わないもの:

- `FAQPage`: 2026年5月から Google 検索で FAQ のリッチリザルトが表示されなくなりました。書いても害はありませんが、表示は期待できないので新しくは足しません
- `HowTo`: リッチリザルトの表示が終了しています

公開前に、Google のリッチリザルトテストと Schema Markup Validator で構文エラーがないことを確認します。テンプレートは templates/jsonld/ にあります。

## 5. スマホの幅（iPhone SE）

Lighthouse の「測るページ」と同じページを、`scripts/check_mobile_width.py` で 320px、375px、390px の幅で調べます。横スクロール、画面からはみ出した要素、ヘッダーの中の折り返しがないことと、スクリーンショットで見出しの改行位置や重なりがないことを確かめます。作り方の決まりと、NG が出たときの直し方は build.md の「スマホの幅」にあります。

```bash
python3 <スキルの場所>/scripts/check_mobile_width.py http://localhost:4321/
```

Lighthouse のモバイル設定は 412px 前後の幅で測るため、点数が満点でも iPhone SE の幅で崩れていることがあります。デザインやヘッダー、メニューを変えたときは、記事の追加だけの場合を除いて、毎回確かめます。

## 6. セキュリティ監査

Cloudflare の security-audit スキルで、サイトのリポジトリ全体の脆弱性を調べ、確定したものを直します。公開前と、機能を追加・変更したときに行います。記事の追加だけのときは行いません。入れ方、頼み方、結果の扱いは security-audit.md にあります。

## 記録

計測結果（測ったページごとの4項目の点数、LCP、CLS、TBT、スマホの幅の確認の結果）、セキュリティ監査の件数と、直した内容をログと SITE.md の「品質の記録」に残します。点数が前回より5点以上下がった変更は、原因を書きます。
