# お問い合わせフォーム

お問い合わせの受け方は、オーナーに4つから選んでもらいます。基本は Google フォームです。サイトと同じ見た目にこだわりたい場合だけ、Cloudflare Email Sending を使って自前で作ります。オーナー向けの説明は docs/forms.md にあります。

## 選び方

ヒアリング（hearing.md の「問い合わせの受け方」）で、次の選択肢を見せます。

| 選択肢 | オーナーの手間 | 見た目 | 費用 | 保守 |
|---|---|---|---|---|
| A. Google フォームをリンクで開く（おすすめ） | 10分 | Google の見た目 | 無料 | 増えない |
| B. Google フォームをお問い合わせページに埋め込む | 10分 | サイトの中に Google のフォームが入る | 無料 | 増えない |
| C. サイトと同じ見た目のフォーム（Cloudflare Email Sending） | 30〜60分。Claude と対話しながら進める | サイトと同じ | 無料の場合と、月5ドルの場合がある | 要保守構成になる |
| D. フォームを置かず、メールアドレスか電話番号を載せる | なし | - | 無料 | 増えない |

- 迷っている場合は A を勧める。B は、ページの表示が少し遅くなることを伝える
- C を選ぶ前に、次の4つを伝えて了承を得る
  1. 導入の手順が多い（Cloudflare の設定画面での操作、秘密の鍵の貼り付け、メールの確認）
  2. メール送信の機能（Email Sending）は、執筆時点で Cloudflare のベータ版
  3. 料金は導入時に確かめる。自分宛ての通知だけなら無料とされているが、無料プランで使えない場合は Workers の有料プラン（月5ドル）が必要
  4. サイトがアクセスのたびに処理する部分を持つので、要保守構成になり、2週間ごとの保守ルーティンを設定する
- formrun、Tally、Resend、Web3Forms などのほかのサービスは、オーナーが名前を挙げた場合だけ扱う（下の「ほかのサービスを頼まれたとき」）

## A・B. Google フォーム

Google フォームはオーナーの Google アカウントで作ります。会社の共有のアカウントがあれば、そちらを勧めます（担当者が変わっても引き継げるため）。

### 使うコネクタ

Google フォームには、Claude の公式のコネクタも、Google 公式の MCP サーバーもありません（2026年10月時点。connectors.md）。そのため、次のように分けます。

- フォームを作る: ブラウザ操作（Claude in Chrome、デスクトップアプリ内のブラウザ）。使えない環境では、拡張機能の導入を案内するか、サイドパネルに貼る指示文を渡すか、画面ごとの手順を案内する（下の「作る」の2）。個人が公開している Google フォームの MCP サーバーは使わない
- 回答を読む: 回答を書き出した Google スプレッドシートを、公式の Google Sheets のコネクタで読む。オーナーが「今月の問い合わせをまとめて」と頼んだときに使う
- フォームやスプレッドシートを探す: 公式の Google Drive のコネクタ

フォームの作成の前に、Google Sheets と Google Drive のコネクタがつながっているかを確かめ、つながっていなければ接続のカードを出してオーナーに認証してもらいます（connectors.md の「使う順番」）。回答の中身（問い合わせた人の個人情報）を Claude が読むことになるので、接続の前にそのことを伝えます。

コネクタだけでフォームの作成から回答の確認まで済ませたいオーナーには、番外編の Tally に Claude の公式のコネクタがあることを伝えてもよい（預け先が増える注意とあわせて）。

### 作る

1. Claude が質問の項目を提案する（お名前、会社名、メールアドレス、電話番号、お問い合わせ内容）。聞く項目は最小限にし、健康、口座番号、マイナンバーのような慎重に扱う情報は聞かない
2. ブラウザを操作できる環境では Claude が forms.google.com でフォームを作る。ブラウザ操作のツールがない、または会話がパソコンにつながっていない場合は、account-setup.md の「ブラウザ操作の準備（Claude in Chrome）」に従い、拡張機能の導入とつなぎ方を案内する。オーナーが導入しない場合は、Claude in Chrome のサイドパネルに貼る指示文（templates/forms/chrome-google-form-prompt.md の `<...>` を埋めたもの）を渡すか、画面ごとの手順を番号付きで案内する
   - Google Drive のコネクタは文書・表・スライドを作れるが、フォームは作れない。Google Sheets のコネクタも同じ。どちらもフォームの作成には使わない
3. 設定
   - 「回答」タブの右上のメニューから「新しい回答についてのメール通知を受け取る」をオンにする
   - 「回答」タブの「スプレッドシートにリンク」で、回答を Google スプレッドシートにも書き出す（一覧での管理と、担当者での手分けに使える）
   - 回答の最後に表示するメッセージを「お問い合わせありがとうございます。◯営業日以内にご連絡します」のようにする
   - フォームの説明欄に、送信内容の使い道とプライバシーポリシーへのリンクを書く
4. オーナー: 「送信」ボタンからリンクをコピーして Claude に渡す。B の場合は「<>」（埋め込み）の HTML を渡す
5. テストで1件送信し、通知メールが届くこと、スプレッドシートに書き出されることを、オーナーと一緒に確かめる。テストの回答は削除する

### サイトに入れる

- A: お問い合わせページと、ヘッダー・フッターのお問い合わせのリンク先を、Google フォームの URL にする。別のタブで開くことと、Google のページに移ることを、ボタンの近くに一言書く（例: 「Google フォームが開きます」）
- B: お問い合わせページにだけ埋め込む。トップページなどほかのページには埋め込まない
  ```html
  <iframe src="<埋め込み用の URL>" title="お問い合わせフォーム" width="100%" height="1200" loading="lazy" style="border:0"></iframe>
  <p><a href="<フォームの URL>">フォームが表示されない場合はこちら</a></p>
  ```
  - `loading="lazy"` で、ページの表示を待たせない
  - 高さはフォームの長さに合わせて調整し、スマホで内側にスクロールが出すぎないようにする
  - Lighthouse で問い合わせページを計測し、点数が下がった場合は理由をオーナーに伝える（quality-gate.md）

### 回答の見方（オーナーへの説明）

- 通知メールが届いたら、Google フォームの「回答」タブか、リンクしたスプレッドシートで内容を見る
- Google Sheets のコネクタがつながっていれば、Claude に「今週の問い合わせを一覧にして」「返信していないものを教えて」と頼める
- 古い回答は、不要になったら「回答」タブやスプレッドシートから削除する。Google に期限なく残るため

## C. 自前のフォーム（Cloudflare Email Sending）

サイトのお問い合わせページに自前のフォームを置き、送信を Cloudflare Workers で受けて、オーナーにメールで知らせます。送信内容はどこにも保存しません。

### 前提

- ドメインが Cloudflare の DNS を使っている（account-setup.md でネームサーバーを Cloudflare に向けている）。Email Sending はこれが条件
- 送信用のレコードは `cf-bounce` のサブドメインに入り、ドメインの受信用の MX レコードは変えない。オーナーが今使っているメール（info@ など）はそのまま使える。ただし Email Routing（受信の転送）は有効にしない。有効にすると受信用の MX が置き換わり、今のメールが受け取れなくなる
- Email Sending は執筆時点でベータ版。手順の前に Cloudflare のドキュメント（Email Service の Get started、料金、ドメインの設定）で最新の状態を確かめる。変わっていたら、`skills/` は直さずに、このサイトでの扱いを SITE.md の「決めたことと理由」に書き、違いを logs/IMPROVEMENTS.md に種類「スキル」で足す（skills-install.md の「守ること」）

### 料金の確かめ方

- Cloudflare の料金ページでは、確認済みの宛先（Destination Addresses）に送るメールは、どのプランでも無料とされている。一方で、Email Sending は Workers の有料プランの機能とも書かれている
- 導入時に、まず無料プランのまま手順を進め、送信のテストが通るかで確かめる。通らない場合は、オーナーに Workers の有料プラン（執筆時点で月5ドル）にするかを聞く。支払いはオーナーの操作
- 確かめた結果を SITE.md の「決めたことと理由」に書く

### 手順

Cloudflare の設定は、Cloudflare の公式の MCP サーバー（connectors.md）で行います。つながっていなければ、最初にオーナーに追加してもらいます。コネクタでできない手順（API が見つからないもの）は、ブラウザ操作に切り替えます。所要時間はオーナーの操作が15〜30分くらい。番号の頭の「オーナー」は、人に任せる4つの操作（SKILL.md）にあたるもの。

1. エージェント: Cloudflare のコネクタがつながっているかを確かめる。つながっていなければ、オーナーにカスタムコネクタの追加を案内する（オーナー: 追加と権限の許可）
2. エージェント: コネクタで、ドメインの DNS の今のレコードを読み取って控える。受信用の MX の行き先（今のメールの会社）を確かめる
3. エージェント: Email Sending にドメインを登録する。コネクタの `search()` で Email Service の API を探し、登録できればコネクタで、見つからなければブラウザで Compute → Email Service → Email Sending の「Onboard Domain」を開く。追加される DNS のレコードを確かめ、受信用の MX が含まれていないことを確認する。登録の確定は、取り消しにくい操作として説明し、オーナーの「はい」を待ってから行う
4. エージェント: コネクタで、通知を受けるアドレスを確認済みの宛先（Destination Addresses）に登録する
5. オーナー: 届いた確認メールの「Verify email address」を押す（どの方法でも、ここは人の操作）
6. エージェント: コネクタで Turnstile のウィジェットを作る。ホスト名に本番のドメインと、確認用の workers.dev のドメインを入れ、モードは Managed にする。サイトキー（公開してよい値）を控える
7. エージェント: 同じ処理の中で、返ってきたシークレットキーをサイトの Worker の Secret `TURNSTILE_SECRET_KEY` として登録する。処理の結果には登録できたかどうかだけを返し、値をチャット、ログ、リポジトリに出さない（connectors.md の「秘密の値は表に出さない」）。オーナーには、Claude が直接登録して画面には表示していないことを伝える。コネクタが使えない場合は、オーナーが Turnstile の画面でシークレットキーをコピーし、Workers の Settings → Variables and Secrets に貼る
8. エージェント: templates/forms/ をもとに実装する
   - `astro-api-contact.ts` を `src/pages/api/contact.ts` に、`contact-handler.ts` を `src/lib/contact-handler.ts` に置く。`@astrojs/cloudflare` を入れ、ほかのページは静的に出力したままにする（stack-selection.md の「SSR を使う場面」、build.md の「一部のページだけ SSR にする場合」）。1ページの LP でも同じ
   - `wrangler-contact.jsonc` の設定（`send_email` の接続、送信回数の制限の `ratelimits`、`vars`）を wrangler.jsonc に足す。`SITE_ORIGINS` には、本番、www、確認用の workers.dev の3つを並べる。送信回数の制限（Rate Limiting の接続）が今のプランで使えずに公開が失敗した場合は、`ratelimits` を外して公開し、Turnstile だけで守ることを SITE.md の「決めたことと理由」に書く
   - `contact-form.html` をお問い合わせページに入れ、`/contact/thanks/`（送信完了のページ）と、`?error=` の理由ごとの案内文を作る
9. エージェント: ローカルで `pnpm run build` を通し、確認用の URL（workers.dev）で公開する。オーナーと一緒にテストで1件送り、通知メールが届くこと、届いたメールに返信すると送信者のアドレス宛てになることを確かめる。迷惑メールのフォルダも見てもらう
10. エージェント: 隠し項目を埋めた送信、Turnstile なしの送信、ほかのサイトからの送信（Origin が違う）が、メールにならないことを確かめる
11. エージェント: 要保守構成の設定を行う（site-maintenance スキルの初期設定）。SITE.md の「技術」の区分を「要保守」にし、SSR のページに `/api/contact` を書く

### 守ること

- 秘密の鍵（Turnstile のシークレットキー）は、リポジトリ、チャット、ログに書かない
- 送信内容を保存する仕組み（データベース、KV、ログ）を足さない。必要になったら、まずオーナーに Google スプレッドシートでの管理を提案する
- 送信者への自動返信は付けない（任意の宛先へのメールは Workers の有料プランが必要で、なりすましの踏み台にもなりうるため）。付けたいと言われたら、費用とリスクを説明してから判断してもらう
- 項目を増やすときは、contact-handler.ts の文字数の上限とメールの本文も合わせて直す

### 困ったとき

| 症状 | 確かめること |
|---|---|
| メールが届かない | 迷惑メールのフォルダ、Destination Addresses の確認が済んでいるか、Email Sending の登録の状態、Workers のログのエラーの種類（`E_SENDER_NOT_VERIFIED`、`E_RECIPIENT_NOT_ALLOWED` など）。どれも Cloudflare のコネクタで読み取れる |
| 送信すると「ロボット確認」のエラーになる | Turnstile のホスト名に、今のドメインが入っているか |
| 無料プランで送れない | 料金の確かめ方に従い、有料プランにするかをオーナーに聞く |

## ほかのサービスを頼まれたとき

formrun、Tally、Resend、Web3Forms、Formspree などを、オーナーが名前を挙げて使いたいと言った場合は、使ってよいが、先に次のことを伝える。

- 問い合わせの内容（名前、メールアドレスなど）を預ける会社が、Google や Cloudflare とは別にもう1つ増える。預け先が増えるほど、流出の入り口が増える
- 運営元、保存場所（国）、保存期間を確かめる。サービスによっては無料プランで保存期間を短くできない、一覧や書き出しが有料、などの制限がある
- サイトのプライバシーポリシーに、預け先と国名を書く

決めたら SITE.md の「決めたことと理由」に、サービス名、理由、保存期間の設定を書く。

## プライバシーポリシー

どの方法でも、サイトにプライバシーポリシーのページを置き、次を書きます。

- 集める情報（お問い合わせの項目）と、使い道（回答のため）
- 処理を任せる会社と国（Google フォームなら Google、自前なら Cloudflare。どちらも米国の会社）
- 問い合わせ先

外国の事業者に個人情報の扱いを任せることについては、個人情報保護法の扱いがあります。ひな形の文面はエージェントが作りますが、正式な文面は専門家に確認するようオーナーに伝えます。
