# 実行ログと改善ループ

サイトのリポジトリに、エージェントが動いた記録（実行ログ）を残します。同じ失敗を繰り返さず、頼まれ方や手順を少しずつよくしていくためです。

## 置くもの

```
logs/
├── IMPROVEMENTS.md          … 改善点の一覧（未対応・対応済み）。templates/IMPROVEMENTS.md から作る
├── YYYY-MM-DD_内容.md        … 1回の実行につき1ファイル。templates/log.md から作る
└── summary/
    ├── YYYY-MM.md           … 古いログを月ごとにまとめた要約（site-review が作る）
    └── YYYY.md              … 古い月の要約を年ごとにまとめたもの
```

監査ログ（記事・お知らせ・サイトの変更の記録）は別の場所 `audit-log/` に置き、ここで扱う実行ログとは分けます（audit-log.md）。site-review の整理の対象にもしません。

## 書くとき

エージェントが動いたら、内容にかかわらず1回につき1ファイルを書きます。

| 起動のしかた | 書く人 | ファイル名の例 |
|---|---|---|
| オーナーの依頼（プロジェクトの会話、チャット） | web-creator、site-content-update | `2026-11-02_news-holiday.md` |
| 公開の失敗（autofix ワークフロー） | GitHub Actions の Claude | `2026-11-02_autofix.md` |
| 保守ルーティン | site-maintenance | `2026-11-01_maintenance.md` |
| 振り返り | site-review | `2026-11-01_review.md` |

質問に答えただけで何も変えなかった場合も、短いログを書きます。オーナーが何を知りたがったかは、README.owner.md やプロンプトを直す材料になります。

## 書き方

templates/log.md に従います。必ず書くのは次の項目です。

- 起動のしかた、使ったスキル、結果（成功 / 一部 / 失敗）
- やったことと、変えたファイル
- 起きたエラーと、どう直したか
- 改善メモ。オーナーに聞き直したこと、手順が足りなかったこと、時間がかかったこと

改善メモのうち、次回以降に直す価値があるものは、logs/IMPROVEMENTS.md に1行で足します。

## 改善ループ

1. 作業の前に読む: SITE.md、logs/IMPROVEMENTS.md の未対応の項目、logs/ の新しいログ3件
2. 作業の中で直す: 今回の作業に関係する未対応の項目があれば、あわせて直す（オーナーの確認が必要なものは聞く）
3. 作業の後に書く: 実行ログを書き、新しい改善点を IMPROVEMENTS.md に足す。直した項目は「対応済み」に移す
4. 定期的に振り返る: site-review スキルで、改善点の整理と、古いログの要約と削除を行う（下の「振り返りの時期」）

IMPROVEMENTS.md の項目は、どこを直すかで2種類に分けます。

- サイト: このサイトのリポジトリで直せるもの（README.owner.md の説明、SITE.md の決まり、ページの作り）
- スキル: tkc310/ai-web-creator のスキルやプロンプトを直すべきもの。オーナーの了承を得て、サイトの URL、会社名、個人情報を除いてから Issue にする

## 振り返りの時期

- 要保守構成のサイト: 毎月1日の保守ルーティンの最後に、site-review も行う
- 静的なサイト: 月に1回の振り返りのスケジュールタスクを勧める（site-review の「スケジュールタスク」）。オーナーが利用量を使いたくない場合は作らず、IMPROVEMENTS.md の未対応が5件を超えたときか、オーナーに「振り返って」と頼まれたときに行う

## 古いログの扱い

ログは放っておくと増え続け、エージェントが読む量も増えます。site-review が次のように整理します。

| 対象 | 扱い |
|---|---|
| 保管期間（既定は90日。SITE.md の「ログ」で変えられる）を過ぎた実行ログ | 月ごとに `logs/summary/YYYY-MM.md` に要約し、元のファイルは削除する |
| 2年より前の月の要約 | 年ごとに `logs/summary/YYYY.md` にまとめ、月の要約は削除する |
| IMPROVEMENTS.md の「対応済み」で、90日を過ぎたもの | その月の要約に移し、一覧から削除する |

- 削除する前に、ログの中の改善点が IMPROVEMENTS.md に、決めたことが SITE.md の「決めたことと理由」に移っているかを確かめる
- 削除はコミットで行うので、GitHub の履歴から元に戻せる。オーナーへの確認はいらないが、何件まとめたかを振り返りのログに書く
- SITE.md の「ログ」で保管期間を「削除しない」にしたサイトでは、要約だけを作り、元のファイルは残す

## 書かないこと

- パスワード、APIトークン、認証コード、Secrets の値
- 問い合わせをくれた人の名前や連絡先など、訪問者の個人情報
- オーナーの個人の連絡先

オーナーの名前や会社名は、サイトのリポジトリが非公開なので書いてかまいません。ただし、スキル側の改善点を Issue にするときは除きます。
