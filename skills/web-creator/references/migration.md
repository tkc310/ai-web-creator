# 既存サイトからの引っ越し

WordPress や STUDIO などで作った今のサイトから、Astro のサイトに引っ越すときに読みます。目標は「検索順位と問い合わせとメールを落とさずに乗り換え、問題があればすぐ戻せること」です。

WordPress と STUDIO は手順を具体的に書いています。そのほかのサービスは、STUDIO と同じく「公開ページから取り出す」手順で進め、エクスポートの機能があればそちらを使います。サービスの機能や料金は変わるため、作業の日にそのサービスのヘルプで確かめます。このファイルと違っていたら、`skills/` は直さずに、このサイトでの扱いを SITE.md の「決めたことと理由」に書き、違いを logs/IMPROVEMENTS.md に種類「スキル」で足します（skills-install.md の「守ること」）。

## 全体の流れ

| # | やること | だれが | 目安 |
|---|---|---|---|
| 1 | 棚卸し（ページ、動く機能、解析、メール、ドメインの契約） | エージェント。契約の確認はオーナー | 1日目 |
| 2 | 中身の取り出しと、新しいサイトの制作 | エージェント | 制作の期間 |
| 3 | URL の対応表と 301 リダイレクト、メタ情報、画像、フォーム、解析 | エージェント | 制作の期間 |
| 4 | ネームサーバーを Cloudflare に移す（サイトはまだ旧サービスのまま。ドメインの契約は今の会社のまま） | オーナーの操作とエージェントの確認 | 切り替えの3日前まで（DNSSEC を使っている場合は5日前まで） |
| 5 | 切り替え（ドメインを新しいサイトに向ける） | エージェント。実行はオーナーの「はい」のあと | 当日 |
| 6 | 切り替え後の確認。問題があれば戻す | エージェント | 当日〜2週間 |
| 7 | 旧サービスの解約 | オーナー | 切り替えの2週間後以降 |

切り替えの日は、問い合わせの多い時間帯を避け、オーナーが連絡を受けられる平日の午前を勧めます。

作成の流れ（SKILL.md の1〜6）との対応: 引っ越しのサイトは、6の公開で workers.dev の確認用の URL まで進めて止め、本番のドメインにはつなぎません。ドメインの切り替えは、この表の4と5で行います。オーナーには、引っ越しを始めるときに「本番のドメインには、オーナーの『はい』があるまでつながない」と伝えます。

## 1. 棚卸し（共通）

1. 自社のサイトであることをオーナーに確かめてから、作業環境から今のサイトに届くかを `curl -sI https://<今のドメイン>/` で確かめる。届かなければ、オーナーに作業環境の通信の許可に今のサイトのホスト（`example.co.jp` と `www.example.co.jp`）を足してもらう（3分くらい。quality-gate.md の「作業環境から本番のサイトに届かないとき」と同じ画面）。届いたら、公開中のページを巡回し、URL、タイトル、meta description、見出し、本文、画像の一覧を作る。sitemap.xml があればそこから、なければトップページからリンクをたどる
2. 次のものを洗い出してオーナーに見せる
   - ページ数と記事数（記事が数千本を超える見込みなら、stack-selection.md の「対象外の判定」に当たる）
   - フォーム、予約、会員機能、コメント、ショップなどの「動く機能」
   - Google アナリティクス、広告のタグ、Search Console の有無と、Search Console の所有権の確認方法
   - ドメインでメールを使っているか（info@ドメイン など）と、メールを預けている会社
   - ドメインの契約先と、DNS を管理している場所（ドメインの会社か、レンタルサーバーか、別の会社か）
3. 動く機能ごとに「同じことを、どう実現するか」を決める。お問い合わせは forms.md の選び方で決める。会員機能とコメント機能は移さない（stack-selection.md の「対象外の判定」）。移さないものと理由は、移行の前にオーナーに伝えて了承を得る
4. 今の DNS のレコードをすべて控える（A、AAAA、CNAME、MX、TXT。TXT には SPF、DKIM、DMARC、Search Console の確認が入っていることが多い）。控えは戻すときにも使うので、`docs/dns-before-migration.md` に残す（秘密の値は入らない）
   - 外から DNS を問い合わせても、名前を知っているレコードしか分からないので、一覧の元にはしない。元にするのは、今 DNS を管理している画面（ドメインの会社かレンタルサーバー）の一覧
   - オーナーに、その画面の DNS のレコードの一覧のスクリーンショットを送ってもらう（5分くらい。行が多ければ複数枚）。画面にゾーンファイルの書き出し（エクスポート）があれば、そのファイルでもよい
   - メールのサービス（Google Workspace、Microsoft 365 など）の管理画面に出ている DKIM の名前（`google._domainkey` など）と照らし合わせ、一覧から漏れていないかを確かめる。照らし合わせられないときは、オーナーにメールのサービスの DKIM の設定画面のスクリーンショットも送ってもらう
   - 一覧の各行を `dig +short <名前> <種類>` で引き、今の値と合っているかを確かめる
5. MX の行き先を確かめる。MX がドメイン名そのもの（`example.co.jp`）を指している場合は、メールがサイトと同じ A レコードのサーバーに届いているので、サイトの向き先を変えるとメールが止まる。ネームサーバーを移したあと、切り替えの前に、段階1の手順6で直す。メールソフトのサーバー名がドメイン名そのものになっていないかも、オーナーに確かめてもらう

## 2. 中身の取り出し

### WordPress

1. オーナーに、管理画面の「ツール → エクスポート」で「すべてのコンテンツ」を選んでエクスポートファイル（XML、WXR 形式）をダウンロードしてもらい、チャットに添付してもらう（管理者の権限が要る）
2. WXR には、投稿、固定ページ、カテゴリ、タグ、カスタムフィールドなどが入る（WordPress の公式の説明）。画像のファイル本体は入らないので、記事の本文と添付ファイルの項目にある `wp-content/uploads/` の URL から取得する
3. 記事を Markdown に変換し、frontmatter（title、date、description、image、tags）を付ける。下書きと非公開の記事は移さないか、`draft: true` にする。どちらにするかはオーナーに聞く
4. ショートコード（`[gallery]` や、プラグインの `[contact-form-7 ...]` など）は Markdown に変換できない。一覧にして、1つずつ置き換え方を決める
5. プラグインで実現していた機能（目次、関連記事、パンくず、SNS のボタンなど）は、必要なものだけを Astro のコードとして作り直す。入れていたプラグインの一覧は、オーナーに管理画面の「プラグイン」のスクリーンショットを送ってもらって確かめる
6. コメントは移さない。残したいコメントがある場合は、記事の本文に引用として入れるかをオーナーと決める

### STUDIO

STUDIO には、サイトのデータを書き出す機能がありません。ヘルプでは、デザイン、ページの情報、ソースコード、CMS のデータ（モデルの構成とアイテムの内容）のどれもエクスポートできず、移行先で作り直す必要があるとされています。書き出せるのは、フォームの回答（CSV）だけです（STUDIO ヘルプ、2026-10-30 確認）。

1. 公開ページを巡回して、文章と画像を取り出す（上の「1. 棚卸し」の1）。表示に JavaScript が要り、ページの HTML に本文が入っていない場合は、ブラウザ操作で表示してから読み取る
2. CMS の記事は、記事の一覧ページと記事ページから取り出す。公開日、カテゴリ、タグがページに表示されていなければ、オーナーに STUDIO の CMS の画面のスクリーンショットを送ってもらって補う
3. 非公開のページや CMS の下書きは、公開ページからは取り出せない。必要なものは、オーナーに STUDIO の編集画面から本文をコピーしてチャットに貼ってもらう
4. デザインは作り直す。今のデザインを引き継ぎたい場合は、主なページのスクリーンショットを撮り、デザイン案（build.md）の参考にする
5. フォームの回答は、解約の前にオーナーにフォームのダッシュボードから CSV でダウンロードしてもらう（下の「7. 旧サービスの解約」）

### そのほかのサービス

- サービスにエクスポートの機能があれば、そちらを優先する。機能の有無は作業の日にそのサービスのヘルプで確かめ、確かめられなければ STUDIO と同じく公開ページから取り出す
- 取り出したものと、取り出せなかったもの（下書き、会員だけのページなど）を、オーナーに一覧で見せる

## 3. URL の対応表と 301 リダイレクト

検索エンジンの評価と、ほかのサイトや SNS からのリンクを引き継ぐため、旧 URL と新 URL の対応表を作ります。

1. 旧 URL の一覧（1の棚卸し）に、新しい URL を1つずつ割り当てる。スラッグ（URL の最後の部分）を旧サイトと同じにできるなら、同じにする方が確実
2. 対応表は `docs/redirects.csv`（旧 URL, 新 URL）に残す
3. URL が変わるものを `public/_redirects` に書く

```
# public/_redirects（Workers の静的アセットで使える）
/archives/123      /news/opening/         301
/company           /about/                301
/blog/:slug        /news/:slug/           301
```

- `_redirects` に書けるのは、固定の転送 2,000 件と、`:slug` などを使う転送 100 件まで（合わせて 2,100 件）。超える場合は Cloudflare の Bulk Redirects を使う
- `_redirects` は、パスの後ろのクエリ文字列（`?p=123` の部分）を条件にできない。クエリ文字列での転送は、Bulk Redirects か Cloudflare のリダイレクトのルールで設定する。どちらにするかは件数を見て決め、設定前にオーナーに伝える
- SSR のページ（Worker のコードが返すページ）には `_redirects` が効かない

WordPress で気をつける URL:

- 初期設定の URL（`/?p=123`）。WXR の各記事の ID から対応を作り、上のクエリ文字列の方法で転送する
- カテゴリやタグの一覧（`/category/<名前>/`、`/tag/<名前>/`）、日付の一覧（`/2025/04/`）、ページ送り（`/page/2/`）。新しいサイトに同じ一覧を作るか、近いページに転送する
- RSS（`/feed/`）。新しいサイトでも RSS を出す場合は、新しい RSS の URL に転送する
- 画像（`/wp-content/uploads/...`）。検索の画像からの流入が多い画像だけ、新しい画像の URL に転送する

STUDIO で気をつける URL:

- CMS の記事の URL の形は、サイトごとの設定で違う。決めつけずに、巡回で集めた実際の URL を対応表の元にする
- 旧サイトの URL の末尾に `/` がない場合（巡回の一覧で確かめる）は、新しい URL（Astro は末尾に `/` が付く形）へ 301 で転送する。Workers の静的アセットは、末尾に `/` がない URL を `/` 付きの URL へ 307（一時的な転送）で送るので、検索の評価を引き継ぐために 301 の行を書く。対応表から URL ごとに書き（`/news/opening /news/opening/ 301`）、`:slug` を使う書き方は、`/` 付きの URL に当たって転送が回り続けないかを確かめてから使う
- 書いたあと、workers.dev の確認用の URL で、`/` なしの URL が 301 で `/` 付きに、`/` 付きの URL が 200 になることを `curl -sI` で確かめる（転送が回り続けないこと）

## 4. メタ情報、画像、フォーム、アクセス解析

### メタ情報

- ページごとのタイトル、meta description、OGP の画像を移す。WordPress で SEO のプラグインを使っていた場合、プラグインで入れた値は WXR のカスタムフィールドに入っていることが多い。見つからなければ、公開ページの `<head>` から読み取る
- 旧サイトで `noindex` にしていたページは、新しいサイトでも検索に出さない設定にするかをオーナーに確かめる
- canonical と sitemap.xml は、新しいサイトの URL で作る（quality-gate.md）

### 画像

- 元の大きさの画像を使う。WordPress は縮小した画像（`-300x200.jpg` のような名前）を自動で作るので、名前の最後に大きさが付いていないものを選ぶ
- すべて site-content-update スキルの scripts/optimize_images.py で、撮影場所などのメタ情報を消してから、軽い形式に変換する
- alt（画像の説明）は旧サイトのものを引き継ぎ、空のものは内容から書く

### フォーム

- 旧サイトのフォーム（WordPress のフォームのプラグイン、STUDIO のフォーム）は移せない。forms.md の選び方で新しいフォームを作り、切り替えの前にテストで1件送る
- 届いた問い合わせの通知先のメールアドレスが、旧サイトと同じかをオーナーと確かめる

### アクセス解析と Search Console

- 新しいサイトのアクセス数は、標準で Cloudflare Web Analytics で見る（analytics.md）
- Google アナリティクスは、旧サイトと同じ測定 ID（`G-` で始まるもの）を新しいサイトに入れると、切り替えの前後の数字を続けて見られる。外部のスクリプトを読み込むので、パフォーマンスの点数が下がることがある。入れた場合と入れない場合の点数を測って伝え、入れるかをオーナーに決めてもらう。入れる場合は、プライバシーポリシーに使っていることを書く（analytics.md）
- Search Console の所有権を、HTML のファイルや `<meta>` のタグで確認している場合は、同じファイルかタグを新しいサイトにも置く。DNS の TXT レコードで確認している場合は、ネームサーバーを移すときに TXT レコードを引き継げばよい
- 旧サービスの管理画面だけで見ていたアクセスの数字は、新しいサイトに移らない。必要ならオーナーに控えておいてもらう

## 5. ドメインと DNS の切り替え

切り替えは2段階に分けます。先にネームサーバーだけを Cloudflare に移し、サイトは旧サービスのまま表示させておきます。こうすると、切り替えの当日に変えるのはサイトのレコードだけになり、戻すのも速くなります。Workers の独自ドメインは、ドメインが Cloudflare で有効になっていることが条件です（Cloudflare のドキュメント）。

### 段階1: ネームサーバーを Cloudflare に移す（切り替えの3日前まで）

移すのはネームサーバー（DNS を管理する場所）だけです。ドメインの契約と更新の支払いは今の会社のままで、Cloudflare 側の費用はかかりません。「3日前」は、ネームサーバーの反映（最大24時間）と、確かめる時間を見込んだものです。DNSSEC を使っている場合は、手順3の待ち時間（多くは1〜2日）が加わるので、5日前までに始めます。

1. エージェント: Cloudflare にドメインを追加し、1の4で控えた DNS のレコードが、すべて Cloudflare に取り込まれているかを1件ずつ比べる。足りないものは足す。特に MX と、SPF・DKIM・DMARC の TXT を確かめる（漏れるとメールが届かなくなる）
2. エージェント: サイトのレコード（ドメインと www の A か CNAME）は、旧サービスを指したまま、プロキシをオフ（DNS only）にしておく。メールのサーバーを指すレコード（`mail` など）も DNS only にする（プロキシをオンにするとメールソフトがつながらない。Cloudflare のドキュメント）
3. オーナー: ドメインの会社で DNSSEC を使っている場合は、先に DNSSEC を止める（DS レコードを消す）。そのあと、古い DS レコードの TTL が切れるまで待つ。エージェントが `dig DS <ドメイン> +short` で何も返らなくなったことを確かめてから、手順4に進む（多くは24〜48時間。待たずに変えると、名前を引けなくなることがある。Cloudflare のドキュメント）
4. オーナー: ドメインの会社の管理画面で、ネームサーバーを Cloudflare が指定する2つに変える（取り消しにくい操作なので、何が起きるかを説明し、「はい」を得てから案内する）。作業は15分くらい
   1. オーナーに、ドメインの会社の管理画面にログインしてもらう（パスワードの入力はオーナー）
   2. ネームサーバーの設定の画面を開いてもらい、スクリーンショットを送ってもらう
   3. エージェントが、スクリーンショットを見て、押す場所と入れる値を1手順ずつ案内する（「ほかのネームサーバーを使う」を選ぶ、1つ目の欄に◯◯を入れる、2つ目の欄に◯◯を入れる、保存する）
   4. ムームードメインならコネクタで変えられる（connectors.md）
5. エージェント: 反映を待つ。ドメインの会社によっては24時間ほどかかる（Cloudflare のドキュメント）。Cloudflare でドメインが Active になったら、旧サイトが表示されること、テストのメールが届くことをオーナーと確かめる
6. エージェント: 1の5で MX がドメイン名そのものを指していた場合は、`mail.<ドメイン>` の A レコード（DNS only、今のメールのサーバーの IP アドレス）を足し、MX をそちらに向け直す。今のメールの会社がメールのサーバー名を案内している場合は、その名前に向ける。テストのメールが届くことを確かめる。メールソフトのサーバー名がドメイン名そのものなら、オーナーに `mail.<ドメイン>`（またはメールの会社の案内する名前）に変えてもらう
7. オーナー: 手順3で DNSSEC を止めた場合は、Active になったあとに Cloudflare で DNSSEC を有効にし、表示された DS レコードをドメインの会社の画面に登録する（エージェントが画面と値を案内する）

### TTL を短くしておく

TTL は、DNS の答えをほかのサーバーが覚えておく時間です。長いままだと、切り替えや戻しが行き渡るまで時間がかかります。

- 段階1のあと、サイトのレコード（DNS only のもの）の TTL を5分（300秒）にする。切り替えの前に、元の TTL の時間以上待つ（元の TTL が1日なら1日。短くした値がほかのサーバーに行き渡るまでの時間）
- 待ったあとは、切り替えも戻しも、たいていは数分で行き渡る
- Cloudflare でプロキシをオンにしたレコードと、Workers の独自ドメインのレコードの TTL は、自動（Auto、300秒）になる（Cloudflare のドキュメント）

### 段階2: 切り替える（当日）

1. エージェント: 新しいサイトを workers.dev の URL で公開し、オーナーに全ページを確認してもらう。Lighthouse と構造化データも確かめる（quality-gate.md）
2. エージェント: 何が起きるか（数分でサイトが新しいものに替わる。替わる間の数分は、ページが表示されないか、証明書の警告が出ることがある）、戻せること（下の「6. 戻し方」）を一文で説明し、オーナーの「はい」を待つ
3. エージェント: サイトのレコード（ドメインと www の旧サービス向けの A か CNAME）を消す。Workers の独自ドメインは、同じ名前の CNAME があると作れない（Cloudflare のドキュメント）。メールのレコード（MX、`mail` の A）は消さない
4. エージェント: `wrangler.jsonc` に独自ドメインを書き、同じコミットで `.github/smoke-test.txt` の URL を本番のドメインに直して公開する（deploy-and-autofix.md の「独自ドメインの接続」。分けると、workers.dev の URL が使えなくなって公開後の確認が失敗する）。www あり・なしの統一の転送も設定する
5. エージェント: 本番のドメインでページが開き、証明書の警告が出ないことを確かめる。アクセス解析を有効にする（analytics.md）

## 6. 切り替え後の確認と戻し方

### 切り替えの当日

- 主なページと、対応表の旧 URL を10件ほど開き、新しいページに 301 で転送されることを確かめる（`curl -sI <旧 URL>`）
- フォームでテストを1件送り、通知が届くことを確かめる
- オーナーにドメインのメールを1通送ってもらい、届くことを確かめる

### 切り替えから2週間

- Search Console で新しい sitemap.xml を送り、404 エラーが増えていないかを1〜2週間見る。増えていたら、対応表の漏れを `_redirects` に足す
- アクセス数と問い合わせの数が、切り替えの前と比べて大きく減っていないかをオーナーと確かめる

### 戻し方

表示の崩れ、フォームが届かない、メールが届かない、のような問題がすぐに直せない場合は、旧サイトに戻してから直します。戻すのも取り消しにくい操作なので、オーナーの「はい」を得てから行います。

1. Workers の独自ドメインを外す（`wrangler.jsonc` の `routes` を消して公開し直すか、Cloudflare のダッシュボードの Domains & Routes で外す）
2. 1の4で控えた、旧サービス向けのサイトのレコードを作り直す
3. TTL が短ければ、数分で旧サイトに戻る。旧サイトが表示されることを確かめ、オーナーに伝える

旧サービスを解約するまでは、この方法でいつでも戻せます。メールのレコード（MX、TXT）は戻す必要がありません。

## 7. 旧サービスの解約

解約はオーナーが行います。エージェントは、解約してよい時期と、その前にすることを伝えます。

- 時期: 切り替えから2週間たち、上の確認で問題がなく、オーナーが了承したあと。それまでは戻せるように旧サービスを残す
- 解約の前に、旧サイトの中身を残しておく
  - WordPress: WXR のファイル、`wp-content/uploads/` の画像、データベースのバックアップ（レンタルサーバーの管理画面で取れる）。オーナーのパソコンか Google ドライブに保存してもらう
  - STUDIO: フォームの回答の CSV をダウンロードしてもらう。STUDIO では独自ドメインでの公開は有料プランの機能です（STUDIO ヘルプ）。プランを下げたあとに独自ドメインで旧サイトに戻せるかの公式の説明は見つからなかったので、戻せなくなる前提で、プランの変更と解約は2週間の確認が終わってからにする
- WordPress をレンタルサーバーで動かしている場合は、次の2つを確かめてから解約する
  - メール: 同じサーバーでメールを預けている場合、サーバーを解約するとメールも使えなくなる。先にメールの移し先を決め、移し終えてから解約する
  - ドメイン: サーバーの契約の特典でドメインを無料で使っている場合は、サーバーの解約で特典が終わることがある（例: エックスサーバーの特典は「サーバー契約が続く限り永久無料」とされている）。解約の前に、ドメインの更新の費用と、移す場合の移管先をオーナーと決める
- STUDIO はメールの機能を持たないため（STUDIO ヘルプ）、STUDIO の解約でメールに影響は出ない。ドメインの契約も STUDIO ではなくドメインの会社にある（STUDIO ではドメインを購入できない。STUDIO ヘルプ）

## 8. 引っ越し後

- SITE.md に、旧サービス名、切り替えの日、リダイレクトの件数、旧サービスを解約した日、旧サイトのバックアップの置き場所を書く
- docs/dns-before-migration.md は、旧サービスを解約したあとも履歴として残す
