# 技術の選定

サイトはすべて Astro で作ります。1ページの LP も、記事の多いメディアも同じです。決めるのは次の3つで、オーナーには技術の名前を選ばせません。

1. このスキルで作れるサイトか（下の「対象外の判定」）
2. 全ページを静的に出力するか、一部のページだけ SSR にするか
3. ページの形（1ページ / 複数ページ / 記事あり）

決めた結果と理由は SITE.md の「技術」と「決めたことと理由」に書きます。オーナーには「1ページのサイトなので、いちばん手間のかからない作り方にします」のように、技術名を出さずに伝えます。

## 判定の順番

```
Q1. 対象外の要件がある？（下の「対象外の判定」の表）
    ある → このスキルでは作らない。SKILL.md の「対応しないもの」の手伝いに進む
           （EC や予約が一部だけで、外部のサービスへのリンクで済む場合は、残りの部分を作る）
    ない ↓
Q2. アクセスのたびにサーバー側で処理が必要なページがある？（下の「SSR を使う場面」）
    ない → Astro の SSG（全ページを静的に出力）… 標準。区分は「静的」
    ある → Astro の SSG ＋ 必要なページだけ SSR。区分は「要保守」
Q3. ページの形は？
    1ページ / 複数ページ / 記事あり → build.md の「ページの形ごとの構成」
```

迷ったら SSG にします。SSR のページはあとから足せますが、足すと保守が増えるためです。1ページの LP から複数ページや記事のあるサイトへの変更も、同じ Astro のリポジトリにページを足すだけで済みます。

## 対象外の判定

このスキルが扱うのは「情報を見せるサイト」です。次のどれかが必要と分かったら対象外にし、その時点でオーナーに伝えます。

| 対象外 | 見分け方 | 理由 |
|---|---|---|
| 記事が数千本を超えるメディア | 今ある記事の数と、1年あたりに増える本数から、数年のうちに数千本を超える見込みがあるか | ビルドは速い（下の「記事の数とビルドの時間」）が、記事の検索や整理、一括の修正を Markdown のファイルで続ける負担が大きくなる |
| 公開後の投稿をお客さまが管理画面から行う受託制作 | 依頼者が制作会社やフリーランスで、公開後の投稿を顧客が AI を使わずに管理画面から行うことが、契約や顧客の方針で決まっている | このスキルで作るサイトには管理画面がない。更新は Claude に頼む前提で作っている |
| 会員機能 | 訪問者が登録やログインをして見るページがある | 個人情報の持ち方や運用を誤るとセキュリティの穴になりやすく、開発に詳しくない利用者には勧められない |
| コメント機能 | 訪問者が記事に書き込める欄がある | 会員機能と同じ理由に加えて、書き込みの管理（荒らしへの対応、削除の依頼）が発生する |
| EC（ネットショップ）、決済 | 商品の注文や支払いをサイトの中で受ける | 決済と注文の管理は業務の仕組みであり、情報を見せるサイトの範囲を超える |
| 予約 | 日時を選んで予約を受け付け、空き状況を管理する | EC と同じく業務の仕組みにあたる |

伝え方と、その後の進め方:

- 対象外であることと理由を、技術名を出さずに一文で伝える（例: 「会員の登録は、個人情報の管理が必要になるため、この方法では作りません」）
- EC と予約は、一部だけが該当する場合（会社のサイトに予約の受付を付けたい、など）に限り、外部の予約サイトや決済リンクへのリンクで済むかを先に提案する。リンクで済むなら、サイトの残りは作る
- 会員機能とコメント機能は、外部のサービスで代わりに作ることも勧めない。このスキルでは作らないと伝える
- 受託制作でも、公開後の更新を顧客が Claude に頼む場合や、制作者が代わりに投稿する場合は対象にする（下の「受託制作のとき」）
- 対象外の部分がどうしても必要な場合は、制作会社への依頼を勧め、SKILL.md の「対応しないもの」の手伝い（制作会社に渡す見本、仕様書、価格の目安）を行う

更新の頻度、書き手の人数、「管理画面がほしい」という希望は、それだけでは対象外の理由にしません。毎日の更新や複数の書き手も、Claude に頼んで更新する運用（site-content-update スキル）で対応できます。管理画面を希望されたら、Google ドキュメントや Claude ドキュメントに書いて渡せば記事になることを先に説明します。

## 記事の数とビルドの時間

記事が千本台までのメディアは、Astro の静的ビルドで足ります。計測では、3,000 本で約 7 秒、1 万本で約 18 秒でした（docs/verification/2026-10-25_media-json-ssr/）。記事の数で対象外にするのは、ビルドの時間ではなく、記事の管理の負担が理由です。

記事が増えても、次のことでビルドを速く保ちます。

- 記事の本文は Markdown にし、MDX や重い部品は必要なページだけにする
- OGP 画像は記事を足したときにだけ作り、毎回のビルドで全部を作り直さない
- ビルドのキャッシュ（`node_modules/.astro` など）を GitHub Actions のキャッシュに残す
- 記事が数千本に近づいたら、公開の前にビルドの時間を測り、実行ログに残す

公開後に記事が数千本を超えそうになった、ビルドが10分を超える、1日に何度も公開してビルド待ちが負担になる、という状況になったら、このスキルの範囲を超えつつあることをオーナーに伝えます。そのうえで、今のサイトをそのまま続けるか、制作会社に CMS での作り直しを頼むかを選んでもらい、頼む場合は仕様書づくりを手伝います。

## Astro の構成

- 向いているもの: 1ページの LP、コーポレートサイト、お知らせやブログがあるサイト、記事が千本台までのメディア
- 構成: SSG（ビルド時に全ページを HTML にする）を前提にします。記事は `src/content/` の Markdown（Content Collections）。ページの形ごとの構成は build.md にあります
- 依存パッケージは最小限にします。原則として `astro`、`@astrojs/sitemap` だけ。UI フレームワーク（React など）や CSS フレームワークは入れません
- 更新: エージェントが Markdown や Astro のファイルを追加・編集する（site-content-update スキル）
- 補足: Astro は2026年1月に Cloudflare に買収されましたが、MIT ライセンスのオープンソースのままで、Cloudflare 以外にも公開できる方針が示されています

### SSR を使う場面

SSR（アクセスのたびにページや処理を実行する）は、要件上どうしても必要なページだけに使います。

- 使ってよい例: お問い合わせフォームの送信を受けてメールを送る処理、サイト内検索の API、外部サービスの最新情報をアクセス時に取得して表示するページ
- 使わない例: 記事一覧、お知らせ、会社概要など、更新時にビルドし直せば済むページ。フォームは Google フォームを基本にし、オーナーがサイトと同じ見た目を選んだ場合だけ SSR にする（forms.md）

SSR を使うときの決まり:

- `@astrojs/cloudflare` アダプターを追加し、SSR にするページ（またはエンドポイント）だけに `export const prerender = false` を書く。サイト全体を `output: 'server'` にはしない
- アダプターを入れると、配信が「ファイルを置くだけ」から「Cloudflare Workers のコードが動く」構成に変わる。Workers の無料枠（1日あたりのリクエスト数、1回あたりの CPU 時間）の範囲に収まるかを確認し、オーナーに伝える
- SSR のページでは、入力値の検証、送信回数の制限、秘密の値（メール送信用のキーなど）を `wrangler secret` で扱うことを必ず行う。秘密の値の登録はオーナーが行う
- 訪問者のデータを保存する仕組み（データベース、KV）は足さない。必要になった場合は、上の「対象外の判定」に当たらないかを先に確かめる
- SSR を使う構成は「要保守構成」になる。site-maintenance スキルに従い、毎月1日と15日の保守ルーティンを設定する（設定しないまま公開しない）

## 受託制作のとき

依頼者が制作会社やフリーランスで、顧客のサイトを作る場合です。

- 対象にするのは、公開後の更新を顧客が Claude に頼む場合と、制作者が代わりに投稿する場合。顧客が AI を使わずに管理画面から投稿することが条件なら、上の「対象外の判定」に当たる。先に、顧客が Claude に原稿を渡して更新する運用（site-content-update）を一度提案し、それでも管理画面での投稿が条件なら対象外として伝える
- LICENSE: 解説記事の購入者は、お客さまのサイトの制作と保守にもスキルを使えます。お客さまごとの追加の購入はありません（LICENSE の 2）。作業の前に、制作者の会社名と、保守の終わりの予定（未定か日付）を聞き、SITE.md の「アカウント」の「受託制作」に「はい（制作者: <会社名>、保守の終わり: <未定 / 日付>）」と書きます。購入の確認のために取り込みを止めることはしません
- お客さまのサイトの非公開のリポジトリに skills/ を置いてよいのは、制作者がそのサイトの制作か保守を続けている間です。制作者が手を離す（保守の契約が終わる、お客さまに引き渡して以後は関わらない）ときは、お客さま自身が解説記事の購入者でなければ、skills/ を除きます。スキルの再配布にあたるためです。お客さまが購入者なら、除かなくてかまいません（LICENSE の 2 と 4）。手順は client-handoff.md
- お客さまに、スキルそのもの（skills/ の写しや zip）を渡すこと、スキルを販売することはできません（LICENSE の 3）
- GitHub と Cloudflare のアカウントは顧客の名義にし、制作者を招待する形を勧める。保守ルーティン（site-maintenance）を動かす人も SITE.md に書く

## 選定後に毎回確認すること

技術の状況は変わるため、制作を始めるときに次を確認します。変わっていたら、`skills/` は直さずに、このサイトでの扱いを SITE.md の「決めたことと理由」に書き、違いを logs/IMPROVEMENTS.md に種類「スキル」で足す（skills-install.md の「守ること」）。

- Astro の最新の安定版とアップグレード時の注意
- Cloudflare Workers の無料枠（リクエスト数、CPU 時間）
- `@astrojs/cloudflare` の設定方法（Astro のメジャーバージョンで変わることがある）

## 構成の区分

| 構成 | 区分 | 保守 |
|---|---|---|
| Astro（SSG のみ）。1ページの LP を含む | 静的 | 月1回の振り返り（site-review）で、Node.js、pnpm、依存パッケージを最新にする（runtime-update） |
| Astro（SSG ＋ 一部 SSR） | 要保守 | 毎月1日と15日の保守ルーティン（site-maintenance）で最新にする（runtime-update） |

区分は SITE.md の「技術」に書きます。
