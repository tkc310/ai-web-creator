# 技術の選定

オーナーには技術の名前を選ばせません。ヒアリングの答えから次の順に判定し、決めた結果と理由を SITE.md の「決めたこと」に書きます。オーナーには「1ページのサイトなので、一番シンプルな作り方にします」のように、技術名を出さずに伝えます。

## 判定の順番

```
Q1. 必要なページは1ページだけで、お知らせやブログはない？
    はい → A. HTML / CSS / JavaScript
    いいえ ↓
Q2. 会員機能（訪問者のログイン）や、訪問者が書き込むコメント機能が必要？
    （会員どうしが交流するコミュニティサイト、会員限定の記事があるサイトなど）
    いいえ → B. Astro
    はい  ↓
Q3. 外部のサービス（会員制のコミュニティサービス、SNS のグループ、コメントの埋め込みサービスなど）へのリンクや埋め込みでは足りない？
    足りる → B. Astro（外部のサービスにつなぐ）
    足りない → C. EmDash（最終手段）

B になった場合だけ:
Q4. アクセスのたびにサーバー側で処理が必要なページがある？（下の「SSR を使う場面」）
    ない → B-1. Astro（SSG のみ）… 標準
    ある → B-2. Astro（SSG ＋ 必要なページだけ SSR）
```

迷ったら B を選びます。A から B、B から C への乗り換えは後からでもできますが、C から戻すのは手間がかかるためです。

記事の数、更新の頻度、書き手の人数、「管理画面がほしい」という希望は、それだけでは C を選ぶ理由にしません。

- 記事が数千本までなら、Astro の静的ビルド（SSG）で足ります。3,000 本で約 7 秒、1 万本で約 18 秒の計測があり、中身の多い実際のサイトでも数十秒〜数分の見込みです（docs/verification/2026-10-25_media-json-ssr/）
- 毎日の更新や複数の書き手も、「Claude に頼んで更新する」運用（site-content-update スキル）で対応できます。管理画面を希望されたら、Googleドキュメントや Claude ドキュメントに書いて渡せば記事になることを先に説明します
- 記事が数千本を超えてビルドが10分を超える、1日に何度も公開してビルド待ちが負担になる、といった状況になったら、仕組みを見直す段階です。ビルドの高速化（下の「記事が増えたとき」）を先に試し、それでも足りなければ EmDash への乗り換えを検討します

## A. HTML / CSS / JavaScript

- 向いているもの: LP、イベント告知、名刺代わりの1ページ
- 構成: `public/` に HTML、CSS、画像を置くだけ。ビルドなし
- 依存パッケージ: なし（デプロイに使う wrangler は GitHub Actions 側で用意する）
- 更新: エージェントが HTML を直接書き換える

## B. Astro

- 向いているもの: コーポレートサイト、お知らせやブログがあるサイト、記事の多いメディア（数千本まで）
- 構成: SSG（ビルド時に全ページを HTML にする）を前提にします。記事は `src/content/` の Markdown（Content Collections）
- 依存パッケージは最小限にします。原則として `astro`、`@astrojs/sitemap` だけ。UIフレームワーク（React など）や CSS フレームワークは入れません

### 記事が増えたとき

記事が数千本になっても、まずは B-1（SSG のみ）のままビルドを速く保ちます（根拠は docs/verification/2026-10-25_media-json-ssr/）。

- 記事の本文は Markdown にし、MDX や重い部品は必要なページだけにする
- OGP 画像は記事を足したときにだけ作り、毎回のビルドで全部を作り直さない
- ビルドのキャッシュ（`node_modules/.astro` など）を GitHub Actions のキャッシュに残す
- 記事が数千本になったら、公開の前にビルドの時間を測り、実行ログに残す

ビルドが10分を超える、1日に何度も公開してビルド待ちが負担になる、という状況が続いたら、仕組みの見直し（ビルドの分け方の変更や、EmDash への乗り換え）をオーナーに提案します。

### SSR を使う場面（B-2）

SSR（アクセスのたびにページや処理を実行する）は、要件上どうしても必要なページだけに使います。

- 使ってよい例: お問い合わせフォームの送信を受けてメールを送る処理、サイト内検索の API、外部サービスの最新情報をアクセス時に取得して表示するページ
- 使わない例: 記事一覧、お知らせ、会社概要など、更新時にビルドし直せば済むページ。フォームは Google フォームを基本にし、オーナーがサイトと同じ見た目を選んだ場合だけ SSR にする（forms.md）

SSR を使うときの決まり:

- `@astrojs/cloudflare` アダプターを追加し、SSR にするページ（またはエンドポイント）だけに `export const prerender = false` を書く。サイト全体を `output: 'server'` にはしない
- アダプターを入れると、配信が「ファイルを置くだけ」から「Cloudflare Workers のコードが動く」構成に変わる。Workers の無料枠（1日あたりのリクエスト数、1回あたりの CPU 時間）の範囲に収まるかを確認し、オーナーに伝える
- SSR のページでは、入力値の検証、送信回数の制限、秘密の値（メール送信用のキーなど）を `wrangler secret` で扱うことを必ず行う。秘密の値の登録はオーナーが行う
- SSR を使う構成は「要保守構成」になる。site-maintenance スキルに従い、2週間ごとの保守ルーティンを設定する（設定しないまま公開しない）
- 更新: エージェントが Markdown を追加・編集する（site-content-update スキル）
- 補足: Astro は2026年1月に Cloudflare に買収されましたが、MIT ライセンスのオープンソースのままで、Cloudflare 以外にも公開できる方針が示されています

## C. EmDash（最終手段）

- 向いているもの: 会員機能やコメント機能が必要なコミュニティサイト（会員どうしの交流、会員限定の記事など）
- 中身: Cloudflare が開発した、Astro ベースのオープンソース CMS（MIT ライセンス）。2026年9月に 1.0 が安定版になりました。Cloudflare では Workers、D1（データベース）、R2（画像などの保存）を使います。ユーザーとログイン（パスキーが標準）、データベースを最初から持つため、会員やコメントのような訪問者のデータを扱う機能の土台にできます
- WordPress のエクスポートファイル（WXR）を取り込む機能と、WordPress に入れる移行用プラグイン（EmDash Exporter）があります
- WordPress のプラグインは EmDash ではそのまま動きません。プラグインで実現していた機能は、エージェントが EmDash のプラグインや Astro のコードとして作り直します（EmDash のリポジトリにある移植用のスキル wordpress-plugin-to-emdash を参照）
- 管理画面のほか、サイトごとに MCP サーバーが用意されるので、エージェントからも記事を操作できます
- サンドボックス化したプラグインを使う場合は Workers の有料プラン（月5ドル〜）が必要です。プラグインを使わなければ無料枠で動かせる場合があります

### EmDash のプラグインは原則使わず、必要な機能は作る

EmDash のプラグインは、2026年10月時点で十数個と少なく、公開から日が浅く安定していないものがあります（例: フォームのプラグイン。forms.md の「EmDash のフォームプラグインは使わない」）。そのため、会員機能やコメント機能など必要な機能は、プラグインを探して入れるのではなく、エージェントがオーナーと相談しながらサイトのコードとして実装します。

- 実装する前に、必要な機能（だれが、何をできるか）を SITE.md の「決めたこと」に書き、オーナーの了承を得る
- 訪問者の個人情報やログインを扱うため、実装のあとに security-audit.md の監査を必ず行う
- プラグインを使う場合は、公開からの期間、更新の頻度、要求する権限（capabilities）を確かめ、理由を SITE.md に書く。プラグインの状況は変わるため、使う前に検索で確認する

C を選んだ場合も「要保守構成」です。site-maintenance スキルに従い、2週間ごとの保守ルーティンを設定します。

### C を最終手段にする理由

- データベースやプラグインを持つ分、本体やプラグインの更新、データベースのバックアップという運用が発生する
- 1.0 になって日が浅く、プラグインの数は WordPress に比べてまだ少ない
- 記事の数や更新の頻度は、EmDash を選ぶ理由にしない。数千本までは Astro の静的ビルドで足りる
- 予約、決済などの機能は、EmDash を選ぶ理由にしない。まず外部のサービス（予約サイト、決済リンク、Googleフォーム）へのリンクで済むかを検討する
- A と B は「ファイルを置くだけ」なので、更新しなくても動き続け、セキュリティの心配も小さい

C を選んだ場合は、2週間ごとに Claude が更新を確認して反映すること、データベースの構造が変わる更新だけはオーナーに確認することを、SITE.md に書いてオーナーに伝えてから進めます。

## 選定後に毎回確認すること

技術の状況は変わるため、制作を始めるときに次を確認し、変わっていたらこのファイルを直してログに残します。

- Astro と EmDash の最新の安定版とアップグレード時の注意
- Cloudflare Workers の無料枠（リクエスト数、CPU 時間）
- `@astrojs/cloudflare` の設定方法（Astro のメジャーバージョンで変わることがある）

## 構成の区分

| 構成 | 区分 | 保守 |
|---|---|---|
| A. HTML | 静的 | 月1回の振り返りで、GitHub Actions の更新を確かめる |
| B-1. Astro（SSG のみ） | 静的 | 月1回の振り返り（site-review）で、Node.js、pnpm、依存パッケージを最新にする（runtime-update） |
| B-2. Astro（一部 SSR） | 要保守 | 2週間ごとの保守ルーティン（site-maintenance）で最新にする（runtime-update） |
| C. EmDash | 要保守 | 同上。データベースの構造が変わる更新はオーナーに確認 |

区分は SITE.md の「技術」に書きます。
