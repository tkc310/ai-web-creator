# 技術の選定

オーナーには技術の名前を選ばせません。ヒアリングの答えから次の順に判定し、決めた結果と理由を SITE.md の「決めたこと」に書きます。オーナーには「1ページのサイトなので、一番シンプルな作り方にします」のように、技術名を出さずに伝えます。

## 判定の順番

```
Q1. 必要なページは1ページだけで、お知らせやブログはない？
    はい → A. HTML / CSS / JavaScript
    いいえ ↓
Q2. 次のどれかに当てはまる？
    ・毎日のように更新する、または複数人が自分で記事を書く
    ・記事が数百本以上ある（WordPress の大きなメディアからの引っ越しを含む）
    ・オーナーや書き手が、管理画面から自分で記事を書きたい
    いいえ → B. Astro
    はい  ↓
Q3. 「Claude に頼んで更新する」運用では本当に足りない？
    （Googleドキュメントに書いて Claude に渡せば記事になる、と説明してから聞く）
    足りる → B. Astro
    足りない → C. EmDash（最終手段）

B になった場合だけ:
Q4. アクセスのたびにサーバー側で処理が必要なページがある？（下の「SSR を使う場面」）
    ない → B-1. Astro（SSG のみ）… 標準
    ある → B-2. Astro（SSG ＋ 必要なページだけ SSR）
```

迷ったら B を選びます。A から B、B から C への乗り換えは後からでもできますが、C から戻すのは手間がかかるためです。

## A. HTML / CSS / JavaScript

- 向いているもの: LP、イベント告知、名刺代わりの1ページ
- 構成: `public/` に HTML、CSS、画像を置くだけ。ビルドなし
- 依存パッケージ: なし（デプロイに使う wrangler は GitHub Actions 側で用意する）
- 更新: エージェントが HTML を直接書き換える

## B. Astro

- 向いているもの: コーポレートサイト、お知らせやブログがあるサイト、数十〜数百ページ
- 構成: SSG（ビルド時に全ページを HTML にする）を前提にします。記事は `src/content/` の Markdown（Content Collections）
- 依存パッケージは最小限にします。原則として `astro`、`@astrojs/sitemap` だけ。UIフレームワーク（React など）や CSS フレームワークは入れません

### SSR を使う場面（B-2）

SSR（アクセスのたびにページや処理を実行する）は、要件上どうしても必要なページだけに使います。

- 使ってよい例: お問い合わせフォームの送信を受けてメールを送る処理、サイト内検索の API、外部サービスの最新情報をアクセス時に取得して表示するページ
- 使わない例: 記事一覧、お知らせ、会社概要など、更新時にビルドし直せば済むページ。フォームは Google フォームを基本にし、オーナーがサイトと同じ見た目を選んだ場合だけ SSR にする（forms.md）

SSR を使うときの決まり:

- `@astrojs/cloudflare` アダプターを追加し、SSR にするページ（またはエンドポイント）だけに `export const prerender = false` を書く。サイト全体を `output: 'server'` にはしない
- アダプターを入れると、配信が「ファイルを置くだけ」から「Cloudflare Workers のコードが動く」構成に変わる。Workers の無料枠（1日あたりのリクエスト数、1回あたりの CPU 時間）の範囲に収まるかを確認し、オーナーに伝える
- SSR のページでは、入力値の検証、送信回数の制限、秘密の値（メール送信用のキーなど）を `wrangler secret` で扱うことを必ず行う。秘密の値の登録はオーナーが行う
- SSR を使う構成は「要保守構成」になる。site-maintenance スキルに従い、Dependabot と2週間ごとの保守ルーティンを設定する（設定しないまま公開しない）
- 更新: エージェントが Markdown を追加・編集する（site-content-update スキル）
- 補足: Astro は2026年1月に Cloudflare に買収されましたが、MIT ライセンスのオープンソースのままで、Cloudflare 以外にも公開できる方針が示されています

## C. EmDash（最終手段）

- 向いているもの: 毎日更新するメディア、複数の書き手がいるサイト、WordPress の大規模サイトからの引っ越しで管理画面が必要な場合
- 中身: Cloudflare が開発した、Astro ベースのオープンソース CMS（MIT ライセンス）。2026年9月に 1.0 が安定版になりました。Cloudflare では Workers、D1（データベース）、R2（画像などの保存）を使います
- WordPress のエクスポートファイル（WXR）を取り込む機能と、WordPress に入れる移行用プラグイン（EmDash Exporter）があります
- WordPress のプラグインは EmDash ではそのまま動きません。プラグインで実現していた機能は、エージェントが EmDash のプラグインや Astro のコードとして作り直します（EmDash のリポジトリにある移植用のスキル wordpress-plugin-to-emdash を参照）
- 管理画面のほか、サイトごとに MCP サーバーが用意されるので、エージェントからも記事を操作できます
- サンドボックス化したプラグインを使う場合は Workers の有料プラン（月5ドル〜）が必要です。プラグインを使わなければ無料枠で動かせる場合があります

C を選んだ場合も「要保守構成」です。site-maintenance スキルに従い、Dependabot と2週間ごとの保守ルーティンを設定します。

### C を最終手段にする理由

- データベースやプラグインを持つ分、本体やプラグインの更新、データベースのバックアップという運用が発生する
- 1.0 になって日が浅く、プラグインの数は WordPress に比べてまだ少ない
- 会員、予約、決済などの機能は、EmDash を選ぶ理由にしない。まず外部のサービス（予約サイト、決済リンク、Googleフォーム）へのリンクで済むかを検討する
- A と B は「ファイルを置くだけ」なので、更新しなくても動き続け、セキュリティの心配も小さい

C を選んだ場合は、2週間ごとに Claude が更新を確認して反映すること、データベースの構造が変わる更新だけはオーナーに確認することを、SITE.md に書いてオーナーに伝えてから進めます。

## 選定後に毎回確認すること

技術の状況は変わるため、制作を始めるときに次を確認し、変わっていたらこのファイルを直してログに残します。

- Astro と EmDash の最新の安定版とアップグレード時の注意
- Cloudflare Workers の無料枠（リクエスト数、CPU 時間）
- `@astrojs/cloudflare` の設定方法（Astro のメジャーバージョンで変わることがある）

## 構成の区分

| 構成 | 区分 | 保守 |
|---|---|---|
| A. HTML | 静的 | 不要（Node.js のサポート期限だけ SITE.md の予定に書く） |
| B-1. Astro（SSG のみ） | 静的 | 不要（同上） |
| B-2. Astro（一部 SSR） | 要保守 | Dependabot ＋ 2週間ごとの保守ルーティン（site-maintenance） |
| C. EmDash | 要保守 | 同上。データベースの構造が変わる更新はオーナーに確認 |

区分は SITE.md の「技術」に書きます。
